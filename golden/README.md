# Golden Tests

End-to-end freeze of the typed pipeline for every supported chain. The suite
replays captured chain fixtures through a local mock endpoint, runs the real
fetcher, converter, and block handler against an embedded headless DefraDB
node, reads every stored document back, and compares the result with the
committed golden files. Any change to what the indexer stores shows up as a
golden diff that has to be reviewed before it lands.

The suite is behind the `integration` build tag and runs via
`make golden-test` (or the per-chain `ethereum-golden-test` /
`tron-golden-test` targets). No network access and no running node are needed:
the only endpoint is the in-process mock server each chain's spec brings,
and it serves exactly the calls the pipeline makes. Anything unexpected
fails loudly, so stray traffic cannot pass silently.

Receipt modes are spec-owned:

- the evm spec runs every chain case twice, once against the batch
  `eth_getBlockReceipts` response and once with that call failing on the
  mock server, which forces the fetcher's per-tx
  `eth_getTransactionReceipt` fallback. The two runs must store identical
  documents: the committed goldens are generated from the batch path, and
  the fallback run compares against the same bytes, so a divergence between
  the paths fails the freeze instead of landing silently.
- the tron spec runs once: the wallet API has a single receipts endpoint
  (`gettransactioninfobyblocknum`) and no fallback path.

Each run gets its own embedded DefraDB store, because the freeze reads the
whole store back.

## Running

```bash
go test -tags=integration ./golden/... -count=1
```

Or through the make umbrella:

```bash
make golden-test
```

## Regenerating goldens

```bash
go test -tags=integration ./golden/... -run Golden -golden-update
```

Regenerate only when the stored output is meant to change, review the
diff, and commit the goldens together with the change that caused it.
Only the chain's primary run (the evm batch path) writes goldens; a later
run can never overwrite them with diverging bytes.

## Layout

```
golden/
  harness_helpers_test.go  suite entry and shared harness: chainSpec
                        interface, case table, shared runner, fixture
                        loading, read-back, stable serialization
  evm_golden_test.go    evm spec: JSON-RPC mock server (with batch-failure
                        mode), hex meta parse, receipt merge assertions
  tron_golden_test.go   tron spec: wallet-API mock server, blockID meta
                        parse, wallet coverage assertions
  ethereum/
    testdata/
      blocks/26293563.json     eth_getBlockByNumber response
      receipts/26293563.json   eth_getBlockReceipts response
      golden/
        block.json
        transaction.json
        log.json
        accessListEntry.json
  tron/
    testdata/
      blocks/HEIGHT.json       getblockbynum body (bare, no envelope)
      receipts/HEIGHT.json     gettransactioninfobyblocknum body
      golden/                  (generated by -golden-update)
```

A block and its receipts are paired by their decimal-height file stem. Both
a full JSON-RPC response body (with the `result` envelope) and a bare
payload work: the loader unwraps the envelope when one is present, and the
wallet API's bare bodies pass through unchanged.

## Capturing a block

### Ethereum

The fixtures are verbatim responses from a real node. Save them under the
decimal height stem:

```bash
# full block by height, transactions included
curl -s $RPC -X POST -H 'Content-Type: application/json' -d \
  '{"jsonrpc":"2.0","id":1,"method":"eth_getBlockByNumber","params":["0xHEIGHT",true]}' \
  > golden/ethereum/testdata/blocks/HEIGHT.json

# receipts for that block, addressed by its hash
curl -s $RPC -X POST -H 'Content-Type: application/json' -d \
  '{"jsonrpc":"2.0","id":1,"method":"eth_getBlockReceipts","params":["0xBLOCKHASH"]}' \
  > golden/ethereum/testdata/receipts/HEIGHT.json
```

Block requirements:

- at least one successful and one failed transaction, so both receipt outcomes
  are frozen
- a complete receipts array: every transaction in the block has its receipt
- every transaction carries `gasUsed`, `cumulativeGasUsed`, and
  `effectiveGasPrice` after the receipt merge, so use a post-London
  (EIP-1559) block

### Tron

The capture script scans backwards from the tip for a block that qualifies
and writes the verbatim wallet-API bodies into
`golden/tron/testdata/`:

```bash
export TRON_RPC_URL=https://api.trongrid.io
export TRON_API_KEY=<your-trongrid-key>   # optional; header sent only when set
make tron-golden-fetch
```

`HEIGHT=<number> make tron-golden-fetch` pins an explicit block and skips
the scan; a pinned block still runs the suitability checks and fails
loudly if it does not qualify. The API key is optional: it is sent as the
`Tron-Pro-Api-Key` header only when set, so providers that embed the key
in the URL (Alchemy) work without a dummy value; the endpoint and the key
are never written into the fixtures.

The freeze is a single-block freeze: the loader reads every file in
`blocks/` and `receipts/`, so the capture script refuses to run when a
fixture already exists (a second capture would silently turn the freeze
into a multi-block one). To recapture deliberately:

```bash
FORCE=1 make tron-golden-fetch
```

A forced run replaces the existing pair, and the old pair is removed only
after the new block qualified, so a failed scan leaves the previous freeze
untouched.

Block requirements (the script enforces them):

- at least one transaction, and a complete receipts response: one
  `gettransactioninfobyblocknum` entry per transaction
- receipts pinned to the block: `blockNumber` and `blockTimeStamp` match
  `block_header.raw_data`
- at least one `SUCCESS` and one failed `contractRet`, so both outcomes
  are frozen
- a `TransferContract` and a `TriggerSmartContract` present
- at least one event log and one internal transfer with a non-zero
  `callValue` (the first `callValueInfo` entry), so the frozen
  `internalTransfer` rows carry a real amount; a TRC-10 movement qualifies
  because its token amount is the `callValue`

## What the goldens compare

Each golden file freezes every stored row of one collection, limited to
chain-data fields. DefraDB artifacts are excluded: no `_docID` and no
relation link fields, so the freeze tracks conversion output rather than
docID scheme details. Rows are sorted by their compact JSON and rendered
with two-space indent, which keeps diffs stable and reviewable.

## Adding a chain

A chain is one `chainSpec` implementation (fixture loading, receipt modes,
mock endpoint, fetcher and converter construction, coverage assertions,
golden collection list) plus one entry in the case table in
`harness_helpers_test.go`. Drop the captured fixtures into
`golden/<chain>/testdata/`,
then regenerate the goldens.
